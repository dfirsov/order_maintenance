# Revision runs, 2026-10-27: per-run tails, a long history, the cross-check

Experiments for the revision of the paper (§5, Appendix E: Table 2 = `tab:eval-summary`,
`tab:native`). The algorithm code was not changed (`src/lean.rs`, `src/avl.rs`, `rust/src/*`);
only drivers and scripts were added or extended. The old result files are untouched, and the new
ones are in `results/rev-2026-10-27/`.

**Machine.** Intel Core Ultra 9 285K (8 performance cores 0–7, 16 efficiency cores), 31 GB RAM,
Linux 7.0.0-38-generic, transparent huge pages `madvise`, governor `powersave`. Every timing run
was pinned to performance core 2 (`taskset -c 2`), and **runs went one at a time**. The earlier
scripts ran 2–4 configurations at once on cores 2, 3, 5, 6, except the cold runs, which also went
one at a time. The core was not isolated: the desktop and an idle `codex` session were running. No
build ran during the timings. The page cache held 15–22 GB, so free memory was 4–12 GB, and the
10⁸ runs (native: 13 GB RSS) made the kernel reclaim page cache.

## What was measured

`compare`, `deletes` and `cold` keep their stdout unchanged: the same CSV columns, still per-operation
minima over the runs. With `TAILS=FILE` set, they also append to `FILE` one row per run and per decade
(or phase), computed from that run's own times. Each row holds the mean, p99, p99.9, p99.99 and
max, the numbers of operations over 10, 50 and 100 µs, and the 2nd and 3rd largest times. A row
`run = min` adds the same statistics of the per-operation minima, so the old method can be compared
directly. The code is `src/tails.rs`.

Two complete replicates were run. Replicate 1 (`results/rev-2026-10-27/`) also holds the cold
runs. Replicate 2 (`results/rev-2026-10-27/rep2/`) was run after the counts of slow operations
were added, and holds everything except the cold runs. Both give the same picture. The tables
below show replicate 2, and replicate 1 is in the appendix at the end.

Definitions, per configuration (3 in-process runs on fresh structures, deterministic workload):
* **mean**: median over the runs of each run's mean (the old `mean_ns`).
* **slowest (per-op min)**: the old figure. Each operation's time is its minimum over the 3 runs,
  and this is the maximum of those minima. No run shows it. In parentheses: the published value
  (old CSVs).
* **run max / p99.9 / p99.99**: each run's own statistic. The median over the 3 runs is given
  first, and the largest run in brackets.

The configurations and arguments are those of `results/run_1e8.sh` (insertions, 10⁸ elements,
last decade 10⁷–10⁸), `results/run.sh` (10⁷, decade 10⁶–10⁷; random and hammer only),
`results/run_queries.sh`, `results/deletes/run.sh` (10⁷) and `results/cold/run.sh` (10⁸). A full 10⁸
run took at most 6.1 minutes per configuration (native random, 3 runs), so 10⁸ was run throughout.

## Findings

1. **Each run's maximum is set by the operating system, not by the algorithm, and it is the same
   for all three implementations.**
   * **Size.** The median over runs of each run's maximum is 0.28–0.31 ms for every
     implementation at 10⁷ (except the amortized baseline's clustered relabelings, 0.53 ms). At
     10⁸, random insertion gives 4.3–6.1 ms for every implementation.
   * **Against the old figure.** That is 30–500 times the old "slowest" figure: native random
     insertion at 10⁸ gives 13.3 µs under the old method and 6.1 ms as a per-run maximum.
   * **Quantized values.** The values recur across implementations and workloads: 0.28–0.31,
     0.70, 0.84, 2.67, 4.28 and 6.11 ms. They also occur in order queries, which allocate nothing
     (0.05–0.2 ms typically, and up to 6.11 ms in one run).
   * **Without any data structure.** `pagetouch` writes one byte to each fresh page of a fresh
     mapping and times each write (`pagetouch.txt`). Of 262,144 first touches, 113–129 take more
     than 100 µs (0.26–0.30 ms, about 1 in 2,000), while the empty timed operations between them
     never exceed 10 µs. At 12 GiB one touch took 3.7 ms, and `/proc/vmstat` counted 17 direct
     reclaim stalls during the test.

   So the 0.3 ms maxima are first-touch page faults, and the ms-scale maxima at 10⁸ come with
   large resident sets and page-cache reclaim. This agrees with the README's earlier note: about
   290 µs stalls, roughly 1 in 3,000 faults, removed by the minimum over runs.
2. **Native has more slow operations per run than the AVL tree.** It touches about 8 times more
   fresh memory per element (112 against 13 bytes), so it takes more of these stalls:
   * random insertion at 10⁶–10⁷: about 120 operations over 100 µs per run, against 8 for the tree;
   * at 10⁷–10⁸: 430 against 170;
   * queue churn deletion: 116 against 0.

   Native's p99.99 per run is still at or below the tree's on insertions: 5.4 against 5.8 µs
   (random, 10⁸) and 2.7 against 3.2 µs (clustered). Its p99.9 is about equal (3.7 against
   3.5 µs) or 2 times the tree's (2.0 against 1.0 µs). Up to p99.99, the per-run tails are close to
   the per-op-min tails: the p99.99 grows by about 20–60%, while the maximum grows by orders of
   magnitude.
3. **The old method reproduces, but not exactly.**
   * **Insertion means** are within 5% of the published ones.
   * **Warm-query and deletion means** are 0–30% lower than published: AVL warm query 0.40
     against 0.57 µs, amortized churn deletion 0.19 against 0.26 µs. Those published runs went
     three at a time and shared the L3 cache; these went one at a time.
   * **The slowest figure varies by up to about 60% between sessions.** Native random insertion
     at 10⁸: published 12.5 µs; now 10.4 µs (replicate 1) and 13.3 µs (replicate 2). Native
     random churn deletion: published 5.9 µs; now 9.4 and 5.9 µs. AVL random insertion: published
     6.6 µs; now 7.6 and 6.9 µs.
   * **The amortized clustered worst case** (5.0–5.2 ms) is a real relabeling, the same in every
     run. It is the only per-run maximum that is algorithmic.
4. **Cold queries reproduce**: native 0.93 / 1.4 µs, AVL 5.9 / 8.4 µs, amortized 0.50 / 0.88 µs
   (published 0.94 / 1.4, 5.5 / 9.0, 0.49 / 0.78). The baselines' cold rows in the paper came from
   `rust/src/bin/cold.rs` on 2026-10-20. Here all three ran with `experiments/lean-design`'s copy
   of that harness, on the same day and core.

## A long history on a small list (`src/bin/longrun.rs`)

The list holds n = 10³ elements while the operations alternate one random deletion and one random
insertion. Two lengths were run: 10⁸ operations (5·10⁷ insertions) and 10⁹ (5·10⁸ insertions).
There is one run per configuration, with no minimum over runs, and 100 windows. Each window
records the mean, p99.99 and max of its deletions and insertions, the resident memory (`VmRSS`),
and for native the resident bytes of each part (`mincore`).

**How memory grows.**
* **All three grow by their handle maps.** Memory grows linearly with the number of insertions,
  not with the list size, because no implementation reuses handles. The rates are native 12 bytes
  per insertion (its handle record, two 32-bit slots and a stamp), AVL 13 (its node arrays are
  indexed by handle), and amortized 20 (its element arrays are indexed by handle).
* **Native's cores stay small.** Its 2.7·10⁵ rebuilds (at 10⁹) leave the structure itself
  bounded in every window:
  * the cores in use: 0.44–0.95 MB;
  * the retired cores kept for reuse: always 14–16, 4.9–5.8 MB;
  * the spare mapping: 0.5 MB.
* **All the growth is handles.** The handle records reach 572 MB after 5·10⁷ insertions and
  6.0 GB after 5·10⁸, at exactly 12.00 bytes per handle. Everything else stays at 7 MB, plus the
  harness's timing buffers.
* **Time does not depend on the history.** Neither the means nor the p99.99 change with it.

Native's window maxima at 10⁸ (median 12.9 µs) are lower than the baselines' (about 270 µs). The
baselines take ordinary first-touch faults as their arrays grow. Native maps handle pages ahead,
one per operation, in `upkeep`, and in this workload that rarely hit a stall.

## The cross-check and the conformance checks, on the current runtime

Logs: `rust/results/xrun_2026-10-27.txt`, `check_2026-10-27.txt`,
`replay_workloads_2026-10-27.txt`, `replay_fuzz_2026-10-27.txt`, produced by
`rust/scripts/conformance.sh 2026-10-27` (new; it reconstructs the earlier commands, whose scripts
were not committed).

**State checked.**
* `lean/.lake/build/bin/xrun` was up to date: `lake build xrun extract` rebuilt nothing.
* `lake exe extract` of the current Lean sources, written to a scratch file, is byte-identical to
  `rust/src/gen.rs`, so the generated code is that of the current machine program.
* The Rust binaries were built from the current runtime (`rust/src/rt.rs`, `alloc.rs`, with the
  runtime fixes of 2026-10-26).

**The checks.**
1. **Lean against Rust (`xrun`): all 9 files identical.** The 9 operation files of
   `scripts/gen_ops.py` are `20 1 mix`, `100 2 mix`, `300 3 churn`, `500 4 mix`, `1000 5 churn`,
   `2000 6 mix`, `2000 7 churn`, `4000 7 mix` and `4000 8 churn`. These are the specifications the
   2026-10-22 re-run used (recovered from the session log; they are the files the paper cites),
   with 13,920 operations in all. Each file was run by Lean's `OM.Machine.exec` (`lake exe xrun`)
   and by the generated code (`target/release/xrun`). Both print one line per operation (and one
   for initialization) with the status, exact step count, answer and peak bit length so far.
   * All 9 outputs were byte-identical (`cmp`), and every line was `ok`.
   * Total: 7,708,854 machine steps, including initialization. The peak bit lengths were 300–449.
2. **`check`: all 12 runs agree with the specification** (`all answers agree with the
   specification`). It runs random operation sequences against a plain list, checking every
   handle and order answer.
   * 200,000 operations with seed 7 in each mode grow, mix and churn: 600,000. This is the
     README's command.
   * 300,000 with seeds 1, 2 and 3 in each mode: 2,700,000. This is the regression form used
     since 2026-10-19.
   * Total: 3.3 million operations.
   * The largest update took 128,373 steps, and peaks reached 660 bits.
   * The paper's "620,000" could not be traced to an exact command. The logs show 3 × 200,000 =
     600,000 with seed 7 and other runs of various sizes. I did not invent the remaining 20,000.
     The figure can be replaced by the counts above.
3. **The 23 stress workloads: all replay with no mismatch** (exit 0). The traces are
   `prototype/trace.py WORKLOAD 200000 --preset proof`, 9,012,453 trace lines, replayed by
   `rust/target/release/replay`, which checks every handle and every order answer.
   * The steps per update (max, mean), query steps and peak bits of all 23 are identical to
     `rust/results/replay_workloads.txt` (2026-10-16). The paper's "9.2 million records" counts
     a different unit; the trace files have 9.01 million lines.
4. **The 1,100 fuzz traces: all replay with no mismatch** (exit 0). They are
   `trace.export_fuzz` seeds 1–1000 (short) and 1–100 (long), with 4,503,828 records and 20,129
   rebuilds. As before, `K_B` was raised to 4 where a trace used 2 or 3.

Everything agreed. The checks took 2 minutes, with the traces generated by 8 Python processes.
